## Separate listen / ping controls (edit, 2026-11-26)
- User's words: "It seems tapping stop and start both create like a burst of audio and both listen silently so I think you need a different button one to begin listening and another button to ping or perhaps you can ping randomly between three and seven seconds"
- Root cause: the old single Start button called `engine.start()` and then immediately `soundTheRoom()`, so beginning to listen always emitted a sounding burst; with only one toggle button, Start and Stop looked and behaved confusingly alike.
- Fix (client only, no schema/action changes): two clearly separated controls. (1) Listening: "Begin listening" opens the microphone ONLY — no sounding, no playback, silent; "Stop listening" closes the microphone ONLY, cancels any ping timer, and makes no sound. Auto-start on agent arming is also silent now. (2) Ping: a distinct amber "Ping now" button (disabled until listening) that is the only on-demand sound — it calls the new `EarEngine.ping()` which plays one `sounding_burst()`, captures its echo into `soundingSamples`/`lastAnalysis`, and the page saves that reading via the existing `save_analysis` action (tagged `source: "ping"`). An "Auto-ping" switch alongside it, when on and listening, pings on a random 3–7 s timer (3,000 + random 0–4,000 ms, rescheduled after each ping, skipped while a queued message is speaking, cancelled on stop/disarm/unmount). Queued-message playback via `speak()` is unchanged and remains agent-driven.

## Hardening pass + colour-only listening indication (edit, 2026-11-26)
- User's words: "Harden it now, before the first exchange" (accepting the audit's recommended hardening) and "improve the space a little bit so after toggling there is some visual indication that it is listening without using text use colors and animations only".
- Audit findings fixed: (1) `get_inbox` now claims atomically — it updates exactly the ids it selected with a `delivered=false` guard and returns only rows it actually claimed, so overlapping fetches cannot double-deliver and a row arriving mid-fetch is never marked delivered unseen. (2) Outbox claiming: new status `claimed` + `claimed_at`; `poll_outbox` atomically claims ONE row (status-guarded update), so two open pages can never speak the same text; claims go stale after 90 s and are re-offered; queued rows carry `expires_at` (15 min TTL) and are swept to `expired` so a text queued for a session that never happened is never spoken uninvited later; `mark_spoken` is a single atomic transition out of pending/claimed, so a duplicate call cannot add a second transcript row. (3) One transmission lock in the engine: all playback (ping, sounding, message) serializes through a single promise chain; `stop()` now stops the actual buffer source, silencing a burst already playing, and playback never resurrects "listening" over a torn-down engine. (4) Listen-before-talk backs off with jittered retries (~20 s across three rounds) instead of playing into a busy channel after 5 s; a ping that finds no clear channel is skipped, a message that finds none throws so it stays queued (claim goes stale, is re-offered) rather than being marked spoken. (5) Dedupe expires: engine `seen` map and server `report_heard` both dedupe only within a 10-minute window (each `speak()` uses a fresh random codec session, so legitimate repeats of short texts like "yes"/"OK" are stored as new messages). (6) Lost-report retry: the page's `report_heard`/`report_failed` go through an in-page queue that drains in order and retries failures every 10 s. (7) True listening state: new `report_listening` action + `listening`/`listening_at` columns; the page reports true on mic open and renews every 20 s while live, false on stop/disarm/unmount; `get_state` exposes `listening` only while the report is <45 s fresh, plus `listening_at`. `active` still means "agent armed". (8) `report_failed` capped at 30 notes/hour server-side. (9) Wake Lock: the engine re-acquires it itself on system release while the session is live and the page visible (the page's visibility handler remains as a second path).
- NOT changed, deliberately: the embedded codec (`ndap.js`) is untouched — the caller/answerer floor discipline and `next_speaker` remain agent-coordination concerns, since the codec's session/next-speaker semantics are shared with Elizabeth's twin and changing them unilaterally would break interop; the house-token check stays off because no house secret has been agreed with the twin (enabling it unilaterally would reject every legitimate peer burst). All pre-existing action names and request/response shapes are unchanged; `get_state`'s response only gains the additive `listening`/`listening_at` fields, and one new action (`report_listening`) is added.
- Visual indication (client + theme only): the page is still exactly one toggle and zero text. While ON and listening, the toggle breathes — a soft pulsing glow in the listening colour (`--accent`) via the `.ear-listening` keyframe animation. When the peer is heard — a decoded message, a real undecodable burst, or the peer's heartbeat sounding found by a periodic `analyze_channel` presence check in the engine (windows overlapping our own playback are skipped) — the toggle track and glow shift to the connected colour (`--connected`) via `.ear-connected`; after 12 s without peer activity it falls back to the listening colour. Toggling OFF removes both classes immediately, so all animation stops. `prefers-reduced-motion` replaces the pulse with a static coloured ring. New tokens: `--connected` in both colour schemes.

## Message-arrival visual indication (edit, 2026-11-26)
- User's words: "When messages arrive, it should also show a visual indicator" — under the same law as the listening indication: colours and animations only, no text, no new controls.
- Implementation: a third colour, `--arrival` (amber; used for nothing else), distinct from the listening colour (`--accent`) and the connected colour (`--connected`). When the engine decodes a peer message (`onHeard`), the toggle flares — `.ear-arrival`, a bright wide pulse (box-shadow expanding to ~120 px) repeated 4 × 1.2 s, with the track itself switching to the arrival colour — then settles back. While the decoded message is still waiting undelivered, the toggle keeps a slow, subtle amber breathing (`.ear-arrival-waiting`, 3.8 s) that clears as soon as the agent fetches it via `get_inbox`; toggling OFF clears both states immediately. `prefers-reduced-motion` replaces both with a static arrival-coloured ring.
- One additive server change, made only because the lingering state needs it: `get_state`'s response gains `inbox_waiting` (count of direction="in", delivered=false messages). No action renamed or removed, no other response shape changed, no schema/migration change (the `delivered` column already existed).

## Stronger listening indication, wordless knob (edit, 2026-11-26)
- User's words: "improve the space a little bit so after toggling there is some visual indication that it is listening without using text use colors and animations only" (repeat of the earlier request; the breathing glow from the hardening pass was on the toggle only and easy to miss across a room).
- Changes (client + theme only; no schema, action, or engine changes): (1) The knob no longer prints ON/OFF — the last visible text on the page is gone; state is carried by knob position and colour alone (the `aria-label`/`aria-checked` remain for assistive tech, never rendered). (2) Radiating rings: while ON, two toggle-shaped rings in the current state colour expand outward from the toggle and fade, staggered 1.3 s apart (`.ear-ripple`), so listening reads from across the room. (3) Level halo: the engine's `onLevel` RMS callback — previously discarded by the page — now drives a blurred halo behind the toggle (`.ear-halo`) whose scale (up to ~1.55×) and opacity swell with the sound the microphone is actually hearing and settle in a quiet room, so the indication reacts to hearing rather than merely asserting a state; the level resets to rest the moment the toggle goes off. (4) One shared state colour: a `--ear-state` custom property on the toggle's wrapper carries arrival (amber) > connected (green) > listening (teal), and the track, breathing glow, rings, and halo all use it, so the whole indication speaks a single colour at any moment. `prefers-reduced-motion` stills the rings to one faint static ring and freezes the halo's transitions, matching the existing static-ring treatment.

## First-exchange failure fix (edit, 2026-11-26)
- User's words: "both phones are toggled to on and I hear the buzzing sound from both of the phones every few seconds and no communication seems to be happening. I did that for a while. and kept the year page open on both phones and they just kept buzzing at each other"
- Evidence (isolated inspection bundle 2b67f99c, production data copy): the queued first message sat in the outbox as `claimed` and was never spoken (zero transcript rows ever — no out, in, or failed entries), while heartbeat pings clearly fired on both phones. Codec verified healthy by local simulation (clean, ping-polluted, and ping-overlapped bursts all decode; per-scan cost measured ~1.4–2.2 s of CPU on a 14 s window).
- Causes fixed: (1) Zombie claims — `poll_outbox` claimed the pending message for ANY polling page, live or not; the captured claim came from a page that was never listening. The client now only polls the outbox while live (`enabled: live`), so a non-listening page can never claim. (2) Decoder thread-hog — detect scans ran over the full 14 s window back-to-back; on a phone CPU that starves the single WebView main thread, collapsing the listen-before-talk sampling so `speak()` kept failing its clear-channel check. Scans now cover the most recent 8 s and are duty-cycled (the gap between attempts is at least the previous attempt's duration, bounded 1.2–6 s). (3) No prompt retry — a failed speak waited out the full claim-stale window; the page now retries up to 3 times at 2.5 s spacing (heartbeat stays suppressed throughout), renewing its claim via the new additive `renew_claim` action before each retry so exclusivity lasts exactly as long as the retrying page lives and no other page can take the message over mid-retries; speak and record are separate phases, so a `mark_spoken` failure retries the recording only and can never re-transmit. (4) Claim-stale shortened 90 s → 45 s (still covers one worst-case speak attempt: ~22 s listen-before-talk + playback). (5) Fragile fallback — with no usable room sounding (the phone's saved ping analysis recommended USE_NDAP6 at −11 dB median SNR), speech fell back to fragile Mode A; it now falls back to Mode B (heavy Reed–Solomon). Per-burst mode choice is local to the transmitter — the codec (`ndap.js`) is byte-untouched and the twin decodes any mode, so interop is unchanged.

## Long-term data behavior
- **Refresh policy**: no scheduled refresh. The page polls `get_state` every ~2 s while open (session state, outbox, transcript tail, room analysis). The owning agent reads new incoming messages on demand via `get_inbox`.
- **Growth**: transcript, inbox and outbox rows are append-only and small (short text turns, capped per the codec's segment caps); no pruning in this build.
- **Ordering**: transcript shown oldest→newest by id; inbox delivered oldest-first; outbox spoken oldest-first (FIFO).
- **Time semantics**: `created_at` timestamps are creation instants rendered viewer-local; message times in the transcript are the viewer's local time.

## Rejected approaches
- **Tried**: Worker-based encode/decode service as the meeting point (original stage-2 shape in the requirements doc)
  **Why rejected**: superseded by the user's own architecture amendment (Nov 26, ~22:03, recorded in the same doc): for the same-room case each house's Space embeds the codec and the air carries only the conversation. The Worker is demoted to an optional later relay and is not built here.
- **Tried**: hand-writing or simplifying a codec in the page
  **Why rejected**: the brief requires embedding the conformance-proven module whole; a rewrite would void the cross-implementation proofs. Only the single specified `analyze_channel` hardening patch is applied.
